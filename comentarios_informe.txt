Problemática Empresarial
Problemática:
   En el sector salud actual, específicamente en el modelo de atención de EsSalud, existe una deficiencia crítica en el monitoreo proactivo de los pacientes con enfermedades crónicas (como hipertensión, diabetes o arritmias) adscritos al Programa de Atención Domiciliaria (PADOMI). Al encontrarse fuera del entorno hospitalario, el modelo de atención vigente es predominantemente reactivo, dependiendo de que el paciente se auto evalúe (usando tensiómetros o smartwatches) y acuda a emergencias cuando la complicación ya es grave. Esta situación se ve agravada por limitaciones tecnológicas, operativas y humanas significativas:
Deficiencias Operativas y Tiempos de Respuesta:
Dependencia de la Revisión Manual: Actualmente, cruzar los datos de los síntomas recientes con el historial clínico del paciente requiere una revisión manual que toma un promedio de 15 a 20 minutos por atención.
Lentitud en Búsqueda de Antecedentes: La falta de un sistema centralizado provoca que un médico demore hasta 10 minutos buscando los antecedentes de un paciente en archivos físicos o sistemas fragmentados antes de poder emitir un diagnóstico preciso.
Ausencia de Alertas Automatizadas: Al depender de consultas programadas o de la iniciativa del paciente, existe un "punto ciego" de horas o incluso días desde que ocurre una lectura anómala en casa hasta que el médico es notificado.
Limitaciones Tecnológicas y de Infraestructura:
Procesamiento Diferido Ineficiente: Los sistemas hospitalarios tradicionales no están diseñados para recibir y procesar flujos de telemetría asíncrona proveniente de dispositivos externos, lo que genera cuellos de botella cuando múltiples pacientes registran sus datos simultáneamente.
Desconexión de Datos: Existe un alto riesgo de subregistro o pérdida de datos críticos al transcribir la información del dispositivo casero al sistema del hospital.
Factores Humanos:
Sobrecarga y fatiga: El personal de salud debe analizar manualmente grandes volúmenes de datos crudos (ej. tablas de presión arterial de todo un mes), lo que aumenta exponencialmente el riesgo de omitir tendencias de deterioro por fatiga visual o exceso de trabajo.

2.2. Lista de requerimientos Funcionales
Módulo 01: Seguridad y control de acceso 
RF-01: El sistema debe permitir el inicio de sesión del personal de salud (médicos y enfermeros de PADOMI) mediante credenciales únicas (usuario y contraseña).
RF-02: El sistema debe bloquear temporalmente la cuenta de un usuario tras 3 intentos fallidos consecutivos de inicio de sesión por motivos de seguridad.
RF-03: El sistema debe gestionar tres roles de usuario con distintos privilegios: Administrador del Sistema, Médico Tratante y Personal de Monitoreo.
RF-04: El sistema debe permitir al rol administrador registrar, modificar y deshabilitar cuentas de personal médico.
RF-05: El sistema debe generar un log de auditoría automático que registre la fecha, hora, usuario y acción realizada (ej. inicio de sesión, modificación de datos).
Módulo 02: Gestión de pacientes
RF-06: El sistema debe permitir el registro de nuevos pacientes crónicos ingresando su DNI, nombres completos, edad, dirección y contacto de emergencia.
RF-07: El sistema debe generar y asignar automáticamente un código único autoincremental a cada paciente al momento de completar su registro, para su correcta identificación en el historial.
RF-08: El sistema debe permitir asociar formalmente a un paciente con un Médico Tratante específico responsable de su caso.
RF-09: El sistema debe permitir el registro y actualización del diagnóstico principal y las comorbilidades del paciente.
RF-10: El sistema debe permitir cambiar el estado de un paciente a "Inactivo" o "Alta" para excluirlo temporal o definitivamente del panel de monitoreo activo.
RF-11: El sistema debe permitir asignar umbrales biométricos de riesgo personalizados para cada paciente (ej. límite máximo de presión arterial específico según su condición).
Módulo 03: Recepción e integración de datos biométricos 
RF-12: El sistema debe permitir la recepción automática y continua de los datos biométricos enviados por los dispositivos de monitoreo de los pacientes.
RF-13: El sistema debe verificar que los datos biométricos recibidos contengan toda la estructura de información obligatoria antes de ser procesados.
RF-14: El sistema debe registrar de cada lectura biométrica: el identificador del paciente, el tipo de métrica (enfermedad o signo), los valores registrados, la unidad de medida y la fecha/hora exacta de la medición.
RF-15: El sistema debe rechazar y descartar automáticamente los registros biométricos entrantes que estén incompletos o presenten formatos de datos inválidos.
RF-16: El sistema debe almacenar el historial completo de todas las lecturas biométricas validadas, vinculados automáticamente al expediente clínico del paciente correspondiente.
RF-17:  El sistema debe permitir la recepción simultánea de múltiples tipos de métricas (ej. presión y glucosa al mismo tiempo) de un mismo paciente en un solo envío.
Módulo 04: Módulo de Triaje Automatizado y Evaluación Clínica
RF-18: El sistema debe identificar dinámicamente el tipo de métrica recibido y aplicar exclusivamente la lógica de validación correspondiente a esa condición clínica (ej. reglas de diabetes para la glucosa, ignorando las reglas de hipertensión).
RF-19: El sistema debe evaluar los valores biométricos recibidos comparándolos matemáticamente contra los umbrales máximos y mínimos configurados para el paciente.
RF-20: El sistema debe clasificar el resultado de la lectura en tres estados de severidad estandarizados: Normal (Verde), Advertencia (Amarillo) o Crítico (Rojo), independientemente de la enfermedad analizada.
RF-21: El sistema debe soportar la agregación de nuevos tipos_metrica (ej. si en el futuro EsSalud decide monitorear la temperatura corporal) mediante la interfaz administrativa, sin necesidad de reprogramar el código fuente del motor de reglas.
RF-22: El sistema debe actualizar el nivel de riesgo global del paciente en la base de datos inmediatamente después de procesar una lectura que resulte en estado "Crítico".
Módulo 05: Módulo de Monitoreo Clínico
RF-23: El sistema debe mostrar al médico una tabla central (Dashboard) con la lista de pacientes, indicando su diagnóstico principal y su estado de riesgo actual.
RF-24: El sistema debe ordenar automáticamente a los pacientes, priorizando en la parte superior a aquellos que presenten métricas en estado "Crítico" o "Advertencia".
RF-25: El sistema debe incluir un buscador en tiempo real (respuesta < 2 segundos) para filtrar pacientes por nombre o DNI.
RF-26: El sistema debe renderizar dinámicamente las unidades de medida en la interfaz gráfica según la enfermedad del paciente (ej. mostrando "mg/dL" si el paciente es diabético, o "mmHg" si es hipertenso).
RF-27: El sistema debe generar gráficos de evolución históricos, permitiendo al médico usar un menú desplegable para alternar entre las diferentes métricas registradas para un mismo paciente (ej. ver curva de glucosa y luego cambiar a curva de peso).
Módulo 06: Gestión de alertas
RF-28: El sistema debe emitir una alerta visual destacada (color rojo) en el dashboard indicando no sólo el nombre del paciente, sino el contexto clínico exacto de la emergencia (ej. "Alerta Glucosa crítica: 320 mg/dL" o "Alerta Presión arterial crítica: 180/110 mmHg").
RF-29: El sistema debe requerir que el usuario médico ejecute una acción afirmativa (clic en "Marcar como Atendido") para silenciar la notificación en curso.
RF-30: El sistema debe registrar un historial inmutable de alertas que detalle el tipo_metrica que falló, el valor crítico registrado, la hora exacta y qué profesional de la salud validó la emergencia.

CU-01: Iniciar Sesión  
Capa 1: Presentación
Es el punto de contacto donde el personal médico o administrativo ingresa sus credenciales.
auth.routes.ts: Define la ruta de acceso (ej. POST /auth/login). Mapea la solicitud hacia el controlador de autenticación.
auth.controller.ts: Recibe el Request con las credenciales, las envía al servicio de aplicación y espera el resultado. Si es exitoso, retorna el Token JWT con un estado 200 OK. Si falla, retorna un 401 Unauthorized.
Capa 2: Aplicación
Orquestación de la seguridad y validación de formatos.
auth.service.ts: Coordina el proceso: llama al repositorio para buscar al usuario por su correo/DNI, solicita a la entidad que valide la contraseña y, si todo es correcto, genera el token de acceso.
login.dto.ts: Valida que el cuerpo de la petición contenga un correo con formato válido y una contraseña que cumpla con el mínimo de caracteres, protegiendo al controlador de datos malformados.
Capa 3: Dominio 
Reglas esenciales de identidad y acceso.
usuario.entity.ts: Entidad pura que representa al usuario. Contiene métodos de validación de negocio, como comparar el hash de la contraseña recibida con el almacenado y verificar si la cuenta está activa o bloqueada.
usuario.repository.ts: Interfaz que define las operaciones necesarias para la autenticación, principalmente el método buscarPorEmail() o buscarPorDni().
Capa 4: Infraestructura 
Detalles de persistencia y herramientas externas (TypeORM/Bcrypt).
usuario.model.ts: Modelo del ORM que define la tabla de usuarios en Azure SQL (columnas para email, password hash, rol, etc.).

3.7 Especificación de casos de uso
Para evitar redundancia técnica, las especificaciones se centran en los Casos de Uso Principales (CU-01 al CU-09). Los casos de uso de inclusión  y extensión se detallan íntegramente dentro de los flujos de sus respectivos casos de uso raíz. 

Caso de Uso 
CU01- Iniciar Sesión en la plataforma 
Descripción 
Permite que el Administrador o el Personal Médico se autentiquen para acceder a las funciones del sistema según su rol. 
Actores
Administrador del Sistema, Personal Médico 
Precondiciones
El usuario debe estar registrado en el sistema y tener estado "Activo". 
RF Asociados
RF-01:El sistema debe permitir el inicio de sesión del personal de salud (médicos y enfermeros de PADOMI) mediante credenciales únicas 
RF-02: El sistema debe bloquear temporalmente la cuenta de un usuario tras 3 intentos fallidos consecutivos de inicio de sesión por motivos de seguridad 
RF-03: El sistema debe gestionar tres roles de usuario con distintos privilegios: Administrador del Sistema, Médico Tratante y Personal de Monitoreo. 
RNF Asociados 
RNF-01: El sistema posee un límite de tiempo de validación y respuesta de inicio de sesión menor a 1 segundo. 
RNF-32: La restricción de bloqueo por intentos fallidos posee una duración inalterable de 30 minutos cronometrados. 
RNF-68: La plataforma exige la generación de un token JWT exclusivamente para la gestión de la sesión .
Flujo Básico 
1. El usuario ingresa su DNI y contraseña en la interfaz de login.
2. El sistema invoca al CU-10 (Validar Credenciales) para verificar la identidad.
3. El sistema genera un Token JWT para la sesión (RNF-68).
4. El sistema registra el acceso en la auditoría (RF-05).
5. El sistema redirige al usuario al Dashboard correspondiente según su rol.
Flujos Alternos 
A1: Credenciales Incorrectas: Si los datos no coinciden, el sistema muestra un mensaje de error de credenciales inválidas (RNF-01) e incrementa el contador de fallos.
A2: Bloqueo de Cuenta: Si el contador llega a 3 fallos consecutivos, el sistema invoca al CU-11 (Bloquear Cuenta) por 30 minutos (RNF-32)
Postcondiciones
El usuario accede al sistema con una sesión activa y segura. 



Caso de Uso 
CU02- Gestionar Cuentas de Personal 
Descripción 
Permite al Administrador del sistema realizar el mantenimiento (registro, edición o inhabilitación) de las cuentas de los profesionales de salud.
Actores
Administrador del Sistema. 
Precondiciones
El Administrador debe haber iniciado sesión exitosamente (CU-01) y contar con los permisos de rol correspondientes. 
RF Asociados
RF-03: El sistema debe gestionar tres roles de usuario con distintos privilegios: Administrador del Sistema, Médico Tratante y Personal de Monitoreo. 
RF-04: El sistema debe permitir al rol administrador registrar, modificar y deshabilitar cuentas de personal médico. 
RF-05: El sistema debe generar un log de auditoría automático que registre la fecha, hora, usuario y acción realizada (ej. inicio de sesión, modificación de datos). 
RNF Asociados 
RNF-02: La latencia interna para la validación de permisos de roles a nivel de servidor está restringida a un máximo de 50 milisegundos. 
RNF-17: El modelo de base de datos de gestión de personal está dimensionado para soportar fluidamente hasta 500 cuentas activas conectadas simultáneamente. 
RNF-34: El modelo lógico contiene un bloqueo estricto anti-auto-desactivación, impidiendo que el último Administrador se elimine a sí mismo. 
RNF-57: Las modificaciones destructivas de usuarios demandan un paso adicional de re-autenticación de seguridad obligatoria. 
Flujo Básico 
1. El Administrador ingresa al módulo de "Gestión de Personal".
2. El sistema recupera y muestra la lista de usuarios actuales (RNF-17).
3. El Administrador selecciona una operación: Crear, Editar o Inactivar.
4. El sistema valida los datos ingresados (DNI único, formato de correo).
5. El sistema persiste los cambios en la base de datos.
6. El sistema invoca automáticamente al CU-17 (Registrar Acción en Auditoría) para grabar la operación (RF-05).
7. El sistema confirma el éxito de la operación en pantalla.
Flujos Alternos 
A1: Intento de auto-eliminación: Si el último Administrador intenta inactivar su propia cuenta, el sistema bloquea la acción y muestra un error “Operación no permitida” (RNF-34).
A2: Usuario ya existente: Si se intenta registrar un DNI que ya existe, el sistema rechaza la operación y notifica al usuario.
A3: Error de red: Si el motor SQL no responde en 3 segundos, el sistema aborta la transacción (RNF-31).
Postcondiciones
La base de datos de personal se actualiza y se genera un registro inmutable en el log de auditoría 





Caso de Uso 
CU-03: Gestionar Catálogo de Métricas
Descripción 
Permite al Administrador gestionar (crear, editar o inactivar) el catálogo de enfermedades y signos vitales que el sistema es capaz de procesar, definiendo sus unidades de medida y parámetros base. 
Actores
Administrador del Sistema. 
Precondiciones
El Administrador debe estar autenticado en la plataforma (CU-01)
RF Asociados
RF-18: El sistema debe identificar dinámicamente el tipo de métrica recibido y aplicar exclusivamente la lógica de validación correspondiente a esa condición clínica.
RF-21: El sistema debe soportar la agregación de nuevos tipos_metrica mediante la interfaz administrativa, sin necesidad de reprogramar el código fuente del motor de reglas. 
RF-26: El sistema debe renderizar dinámicamente las unidades de medida en la interfaz gráfica según la enfermedad del paciente (ej. mostrando "mg/dL" si el paciente es diabético, o "mmHg" si es hipertenso). 
RNF Asociados 
RNF-49: La configuración administrativa bloquea mediante índice único (Unique Constraint) cualquier intento de colisión de nombres al crear métricas repetidas. 
RNF-72: La configuración matemática cuenta con restricciones lógicas algorítmicas que prohíben categóricamente establecer un "mínimo" numérico superior a un "máximo". 
RNF-75: Almacenamiento del diccionario de métricas en caché de acceso ultrarrápido (Redis).
Flujo Básico 
1. El Administrador ingresa al módulo de "Catálogo de Métricas".
2. El sistema recupera la lista de métricas disponibles desde la caché de Redis para mayor velocidad (RNF-75).
3. El Administrador selecciona una operación: Crear Nueva Métrica, Editar o Inactivar.
4. El Administrador define el nombre, la unidad de medida y los rangos estándar.
5. El sistema valida que no exista otra métrica con el mismo nombre (RNF-49) y que la lógica numérica sea coherente (RNF-72).
6. El sistema guarda la configuración y actualiza la caché.
7. El sistema invoca al CU-17 (Registrar Acción en Auditoría) para dejar constancia del cambio.
Flujos Alternos 
A1: Métrica en uso: Si el Administrador intenta inactivar una métrica que ya está asignada a pacientes con monitoreo activo, el sistema rechaza la acción para evitar inconsistencias clínicas.
A2: Incoherencia Numérica: Si el usuario intenta guardar un límite mínimo mayor al máximo, el sistema dispara una alerta visual y bloquea el registro (RNF-72).
Postcondiciones
El motor de reglas queda habilitado para procesar e interpretar los nuevos tipos de datos biométricos de forma inmediata. 



Caso de Uso 
CU-04: Registrar Paciente Crónico 
Descripción 
Permite al Personal Médico ingresar a un nuevo paciente de PADOMI al sistema, capturando sus datos personales, clínicos y asignándole un médico tratante responsable. 
Actores
Personal Médico. 
Precondiciones
El médico debe estar autenticado (CU-01) y el paciente no debe existir previamente en la base de datos. 
RF Asociados
RF-06: El sistema debe permitir el registro de nuevos pacientes crónicos ingresando su DNI, nombres completos, edad, dirección y contacto de emergencia 
RF-07: El sistema debe generar y asignar automáticamente un código único autoincremental a cada paciente al momento de completar su registro, para su correcta identificación en el historial. 
RF-08: El sistema debe permitir asociar formalmente a un paciente con un Médico Tratante específico responsable de su caso. 
RF-09: El sistema debe permitir el registro y actualización del diagnóstico principal y las comorbilidades del paciente. 
RNF Asociados 
RNF-04: La validación sintáctica estructural del DNI exige un tiempo de procesamiento del lado del cliente (Frontend) menor a 200 milisegundos antes de autorizar el envío. 
RNF-19: El diseño de esquema de datos de la aplicación estandariza una longitud fija y estricta (ej. PAC-0000) para los códigos de paciente. 
RNF-20: La regla de negocio exige emitir una alerta preventiva de saturación si un médico supera el límite de 500 pacientes asignados. 
RNF-59: El flujo de registro ejecuta una sanitización automática pre-envío eliminando metacaracteres no numéricos del documento DNI. 
Flujo Básico 
1. El médico ingresa al módulo de "Pacientes" y selecciona "Nuevo Registro".
2. El sistema valida en tiempo real la estructura del DNI (RNF-04) y limpia caracteres no numéricos (RNF-59).

Análisis de Arquitecturas Evaluadas
Para la definición de la infraestructura del sistema PADOMI, se evaluaron cuatro enfoques arquitectónicos cruzando los requerimientos de telemetría de misión crítica con la viabilidad operativa y financiera del proyecto:
1.Arquitectura Monolítica 
Es un modelo en el que la interfaz de usuario, la lógica de negocio y el acceso a los datos están combinados en un único código base y compilados en un solo programa ejecutable que se despliega en un único servidor.
Ventajas: Curva de aprendizaje mínima para el equipo de desarrollo. El despliegue de producción es sumamente sencillo y económico (requiere un solo servicio de alojamiento). Facilita las pruebas de integración end-to-end al no tener dependencias de red internas.
Desventajas: Carencia de escalabilidad selectiva. Ante una alta concurrencia (ej. 200 JSON por segundo desde dispositivos IoT), los hilos del servidor se agotan, provocando un colapso general del sistema que inhabilita incluso las funciones administrativas de bajo consumo.
2. Arquitectura por Capas (Layers)
Es un patrón de diseño lógico que organiza el código en divisiones horizontales (Presentación, Lógica de Negocio y Datos). El flujo de información es unidireccional, garantizando que cada capa tiene una responsabilidad estricta.
Ventajas: Fomenta un código ordenado, mantenible y la separación de responsabilidades. Permite al equipo paralelizar el desarrollo estructurando el backend de forma estandarizada e independiente de la base de datos.
Desventajas: Es una solución de diseño de software, no de infraestructura. A nivel de despliegue, la aplicación generalmente sigue operando en un solo bloque físico, por lo que hereda la misma vulnerabilidad de colapso por saturación de red que un monolito tradicional.
3. Arquitectura Orientada a Servicios:
Diseño a nivel corporativo utilizado para integrar múltiples aplicaciones empresariales heterogéneas preexistentes.
Ventajas: Excelente para la interoperabilidad entre sistemas heredados de grandes organizaciones y para la reutilización de servicios en corporaciones con múltiples departamentos autónomos.
Desventajas: Representa una sobre ingeniería extrema para un proyecto desarrollado desde cero. Su implementación implica una complejidad operativa injustificable, requerimientos de hardware pesados y costos de licenciamiento inasumibles para un entorno académico.
4. Arquitectura Orientada a Microservicios 
Enfoque donde el sistema se descompone en pequeños servicios autónomos, débilmente acoplados, cada uno con su propia base de datos y ejecutando un proceso de negocio único.
Ventajas: Escalabilidad y resiliencia absolutas. Permite asignar recursos computacionales exclusivamente al módulo de "Ingesta IoT" sin afectar al "Dashboard Médico". Si un microservicio falla, el resto del sistema sigue operando con normalidad.
Desventajas: Complejidad operativa crítica (DevOps). Exige gestionar consistencia eventual de datos, rastreo distribuido y configurar API Gateways. Además, mantener múltiples bases de datos y servidores simultáneos genera un costo de infraestructura en la nube (Cloud Hosting) que resulta financieramente inviable y excede cualquier nivel gratuito estudiantil.
Justificación de la Arquitectura Seleccionada
Arquitectura Híbrida (Monolito Modular por Capas + Ingesta Serverless)
La selección de la arquitectura base para el "Sistema de Telemetría y Gestión de Alertas para Salud Crítica (PADOMI)" representa el desafío de ingeniería más crítico del proyecto. Tras evaluar los enfoques tradicionales (Monolítico, Capas, SOA y Microservicios), se ha determinado que adoptar un único paradigma de forma purista condena al proyecto al fracaso operativo (por saturación de recursos) o al fracaso financiero (por sobrecostos de infraestructura).
Por consiguiente, se ha diseñado una Arquitectura Híbrida Orientada a Eventos, la cual fusiona la mantenibilidad de un Monolito Modular estructurado en Capas para el núcleo administrativo, con la elasticidad infinita de un Microservicio Serverless (Azure Functions) para la ingesta de telemetría IoT. Esta decisión se fundamenta a través de cinco dimensiones de análisis crítico:
1. Dimensión de Concurrencia y Resolución del Cuello de Botella
El análisis de los Requerimientos No Funcionales del sistema revela la existencia de dos patrones de tráfico de red mutuamente excluyentes que deben coexistir en la misma plataforma:
Tráfico Transaccional Administrativo (Bajo-Moderado): Interacciones de los médicos con el sistema, tales como la autenticación de usuarios, la actualización de historiales clínicos y la gestión de umbrales. Este tráfico requiere alta consistencia de datos pero tiene una tasa de peticiones predecible.
Tráfico de Telemetría IoT (Alta Concurrencia): Envíos constantes e impredecibles de paquetes JSON emitidos por los dispositivos de los pacientes. Según el RNF-23, el sistema debe soportar hasta 200 ingestas por segundo.
Implementar una Arquitectura Monolítica pura para ambos flujos representa un riesgo inminente de inoperatividad . Si los miles de dispositivos envían datos simultáneamente, agotarían rápidamente los hilos de ejecución disponibles y las conexiones a la base de datos en el servidor principal. Como consecuencia directa, si un médico intenta ingresar al Dashboard durante un pico de telemetría, el sistema no responderá, impidiendo la atención de emergencias. La solución arquitectónica adoptada mitiga este riesgo aislando la carga pesada mediante la separación del cómputo.
2. Dimensión de Resiliencia: El Escudo Serverless (Azure Functions)
Para evitar la saturación del núcleo del sistema, se ha delegado la responsabilidad exclusiva de la ingesta de datos a una capa externa utilizando tecnología Serverless (Azure Functions). Esta capa actúa como un "Escudo Perimetral" o amortiguador frente al tráfico del hardware.
Aislamiento de Carga: Cuando el sistema recibe las 200 peticiones por segundo, es la infraestructura distribuida de la nube (Azure) la que escala horizontalmente en milisegundos para absorber el impacto. La función Serverless intercepta el JSON, ejecuta las validaciones de seguridad (peso, sintaxis) y encola el dato procesado.
Protección del Servidor Central: Al delegar esta tarea de alto consumo de CPU a Azure Functions, el servidor donde reside el Core Médico se mantiene en estado óptimo, con el 100% de su memoria RAM y capacidad de procesamiento dedicada exclusivamente a atender las consultas de los médicos y mantener vivas las conexiones de alertas en tiempo real (WebSockets).
3. Dimensión de Mantenibilidad y Calidad de Código (Monolito Modular por Capas)
Si bien el problema de escalabilidad del IoT podría resolverse implementando una Arquitectura de Microservicios pura para todo el sistema, dicha decisión fue descartada por su desproporcionada complejidad. Dividir la gestión de pacientes, médicos, umbrales y auditoría en múltiples microservicios introduciría problemas de redes (latencia interna), exigiría manejar transacciones distribuidas y requeriría estrategias complejas de consistencia eventual que no aportan valor real al negocio hospitalario.
Para centralizar estas reglas de negocio, se ha optado por un Monolito Modular estructurado internamente en Capas.
Separación de Responsabilidades: El código del backend se divide estrictamente en Capa de Presentación (Controladores API), Capa de Negocio (Servicios y Lógica Médica) y Capa de Acceso a Datos (Repositorios y ORM).
Desarrollo Ágil: Esta estructura permite que el equipo de desarrollo universitario trabaje de forma simultánea sin generar conflictos en el código fuente. A nivel de despliegue físico, se comporta como un monolito (un solo servidor, fácil de monitorear y actualizar), pero a nivel lógico, tiene la limpieza y el desacoplamiento de un sistema de nivel empresarial.
4. Dimensión de Viabilidad Financiera y Sostenibilidad
En el contexto de un proyecto desarrollado por estudiantes universitarios, y proyectado para una entidad de salud pública (EsSalud) donde la optimización de recursos presupuestarios es vital, el factor financiero de la arquitectura es decisivo.
El problema del sobre-aprovisionamiento: Alojar un sistema de telemetría en servidores tradicionales requeriría rentar máquinas virtuales de muy alta capacidad para soportar los picos de tráfico. Sin embargo, durante las horas de madrugada o de baja actividad, dichos servidores estarían ociosos, generando un gasto fijo innecesario.
Eficiencia del Pago por Consumo: La integración de la capa Serverless transforma los costos fijos en costos variables. Azure Functions factura únicamente por los milisegundos exactos en los que el código se ejecuta. Si el tráfico IoT disminuye, el costo de la infraestructura de ingesta se reduce automáticamente a cero. Esta arquitectura híbrida garantiza que el crecimiento exponencial de los pacientes monitoreados no se traduzca en un gasto de infraestructura descontrolado, logrando una viabilidad financiera a largo plazo insuperable por otros modelos.
5. Dimensión de Garantía de Alertas Clínicas (WebSockets Ininterrumpidos)
El objetivo supremo del proyecto PADOMI no es solo guardar datos, sino salvar vidas a través de la emisión de notificaciones de riesgo con una latencia menor. Para lograr esto, el frontend (React) mantiene una conexión bidireccional persistente (WebSockets) con el backend. Al emplear esta Arquitectura Híbrida, se garantiza que el canal de WebSockets jamás sea interrumpido por operaciones de entrada/salida bloqueantes provenientes del IoT. El flujo de telemetría ocurre de manera asíncrona, permitiendo que el motor de reglas evalúe el peligro y empuje la alerta visual (Color Rojo) a la pantalla del médico con una fluidez inmediata, cumpliendo estrictamente con el requerimiento de misión crítica del sector salud.
Conclusión Arquitectónica: La Arquitectura Híbrida propuesta se posiciona como la única alternativa que satisface integralmente las necesidades del proyecto. Rechaza la rigidez y vulnerabilidad del Monolito tradicional, evita la complejidad operativa y el alto costo de los Microservicios puros, y desecha la sobre ingeniería de un modelo SOA. Al fusionar la escalabilidad elástica de Azure Functions con la robustez y mantenibilidad de un backend ordenado por capas, se entrega una plataforma tecnológica resiliente, segura, altamente rentable y lista para revolucionar el modelo de atención domiciliaria de EsSalud.

-- USUARIO
CREATE TABLE Usuario (
    id UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    codigo NVARCHAR(20) NULL UNIQUE, -- Ejemplo: USU-0001 (opcional)
    dni CHAR(8) NOT NULL UNIQUE,     -- ¡Nuevo campo agregado!
    nombre NVARCHAR(100) NOT NULL,
    apellido NVARCHAR(100) NOT NULL,
    email NVARCHAR(100) NOT NULL UNIQUE,
    passwordHash NVARCHAR(255) NOT NULL,
    rol NVARCHAR(30) NOT NULL, -- 'MEDICO', 'ENFERMERO', 'ADMINISTRATIVO'
    activo BIT NOT NULL DEFAULT 1,
    especialidad NVARCHAR(100) NULL
);

-- PACIENTE
CREATE TABLE Paciente (
    id UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    codigo NVARCHAR(20) NOT NULL UNIQUE, -- Ejemplo: PAC-0001
    dni CHAR(8) NOT NULL UNIQUE,
    nombres NVARCHAR(100) NOT NULL,
    edad INT NOT NULL,
    diagnostico NVARCHAR(255),
    medicoAsignadoId UNIQUEIDENTIFIER NOT NULL,
    FOREIGN KEY (medicoAsignadoId) REFERENCES Usuario(id)
);

-- METRICA
CREATE TABLE Metrica (
    id UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    codigo NVARCHAR(20) NOT NULL UNIQUE, -- Ejemplo: MET-0001
    nombre NVARCHAR(100) NOT NULL UNIQUE,
    unidad NVARCHAR(20) NOT NULL,
    descripcion NVARCHAR(255),
    rangoMin FLOAT NOT NULL,
    rangoMax FLOAT NOT NULL
);

-- ENFERMEDAD CRONICA
CREATE TABLE EnfermedadCronica (
    id UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    codigo NVARCHAR(20) NOT NULL UNIQUE, -- Ejemplo: ENF-0001
    nombre NVARCHAR(100) NOT NULL UNIQUE,
    descripcion NVARCHAR(255)
);

-- PACIENTE-ENFERMEDAD (relación N:M)
CREATE TABLE PacienteEnfermedad (
    pacienteId UNIQUEIDENTIFIER NOT NULL,
    enfermedadId UNIQUEIDENTIFIER NOT NULL,
    PRIMARY KEY (pacienteId, enfermedadId),
    FOREIGN KEY (pacienteId) REFERENCES Paciente(id),
    FOREIGN KEY (enfermedadId) REFERENCES EnfermedadCronica(id)
);

-- UMBRAL (personalizado por paciente y métrica)
CREATE TABLE Umbral (
    id UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    codigo NVARCHAR(20) NULL UNIQUE, -- Ejemplo: UMB-0001 (opcional)
    pacienteId UNIQUEIDENTIFIER NOT NULL,
    metricaId UNIQUEIDENTIFIER NOT NULL,
    valorMin FLOAT NOT NULL,
    valorMax FLOAT NOT NULL,
    FOREIGN KEY (pacienteId) REFERENCES Paciente(id),
    FOREIGN KEY (metricaId) REFERENCES Metrica(id),
    CONSTRAINT UQ_Umbral_Paciente_Metrica UNIQUE (pacienteId, metricaId)
);

-- LECTURA
CREATE TABLE Lectura (
    id UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    codigo NVARCHAR(20) NOT NULL UNIQUE, -- Ejemplo: LEC-0001
    pacienteId UNIQUEIDENTIFIER NOT NULL,
    metricaId UNIQUEIDENTIFIER NOT NULL,
    valor FLOAT NOT NULL,
    fecha DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
    FOREIGN KEY (pacienteId) REFERENCES Paciente(id),
    FOREIGN KEY (metricaId) REFERENCES Metrica(id)
);

-- ALERTA
CREATE TABLE Alerta (
    id UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    codigo NVARCHAR(20) NOT NULL UNIQUE, -- Ejemplo: ALT-0001
    pacienteId UNIQUEIDENTIFIER NOT NULL,
    lecturaId UNIQUEIDENTIFIER NOT NULL,
    severidad NVARCHAR(20) NOT NULL, -- 'NORMAL', 'ADVERTENCIA', 'CRITICO'
    mensaje NVARCHAR(255),
    fecha DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
    atendida BIT NOT NULL DEFAULT 0,
    FOREIGN KEY (pacienteId) REFERENCES Paciente(id),
    FOREIGN KEY (lecturaId) REFERENCES Lectura(id)
);

-- EVALUACION
CREATE TABLE Evaluacion (
    id UNIQUEIDENTIFIER PRIMARY KEY DEFAULT NEWID(),
    codigo NVARCHAR(20) NOT NULL UNIQUE, -- Ejemplo: EVA-0001
    pacienteId UNIQUEIDENTIFIER NOT NULL,
    medicoId UNIQUEIDENTIFIER NOT NULL,
    fecha DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
    resumen NVARCHAR(500),
    recomendaciones NVARCHAR(500),
    FOREIGN KEY (pacienteId) REFERENCES Paciente(id),
    FOREIGN KEY (medicoId) REFERENCES Usuario(id)
);
